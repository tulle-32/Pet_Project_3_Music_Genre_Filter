# Как устроен доступ к музыке ВКонтакте

Документ отвечает на вопрос, который выглядит простым: «почему нельзя просто
зайти по ссылке и забрать список?». Ответ определяет всю архитектуру проекта,
поэтому он записан отдельно.

---

## Что происходит при открытии страницы с музыкой

Когда в браузере открывается `vk.ru/audios183275836`, происходит **не один
запрос, а несколько, и они разные**. Ниже — актуальная картина, проверенная
разведкой (`music vk probe`, v0.5.1, инструмент с тех пор убран из
репозитория — Р-016) и полным HAR-снимком настоящей сессии браузера
(2026-08-24); более ранняя версия этого документа описывала другой,
устаревший адрес (`m.vk.ru/audio act=load_section`) — см. Р-014 в
`docs/DECISIONS.md`.

```
  Твой браузер                                        Серверы VK
  (залогинен, cookies есть)

       │  ① GET /audios183275836                          │
       │─────────────────────────────────────────────────▶│
       │                                                  │
       │      HTML-каркас страницы + куча JS, треков нет  │
       │◀─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ │
       │                                                  │
       │  ② JS сам находит/подтверждает access_token      │
       │     и делает POST web.api.vk.ru/method/          │
       │     batch.call → внутри catalog.getAudio          │
       │─────────────────────────────────────────────────▶│
       │                                                  │
       │      первая порция треков (≈20) + section_id     │
       │◀─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ │
       │                                                  │
       │  ③ POST catalog.getSection с тем же access_token,│
       │     section_id и курсором start_from — на каждую │
       │     следующую порцию треков                       │
```

Первый запрос отдаёт пустой каркас плюс JavaScript. Треки приезжают вторым
запросом — на внутренний адрес `web.api.vk.ru`, и **только если у браузера
есть годная cookie-сессия и `access_token`**. Программа без сессии получит
на шаге ② не треки, а страницу с проверкой "не бот ли ты".

Ключевая сложность — именно `access_token` (строка вида `vk1.a....`).
Разбор полного HAR-снимка показал: этот токен нигде не рождается на виду.
Его нет в HTML страницы; единственный найденный вызов, где он фигурирует
до использования (`login.vk.ru/?act=web_token`), **подтверждает** уже
готовый токен, а не выдаёт новый — вход и выход буквально совпадают.
Значит токен либо получен в момент входа в аккаунт, которого нет в записи
трафика, либо хранится в браузере (localStorage/IndexedDB) — а это в
принципе не видно снаружи, никаким снифером сети. Подробный разбор — Р-014.

Из этого следуют четыре вещи:

1. **Адрес второго запроса внутренний.** Это не документированный API, у него
   нет обещаний обратной совместимости. Он может измениться в любой момент, и
   всё, что на него завязано, сломается молча.
2. **Нужна настоящая, уже залогиненная сессия.** Причём именно настоящая:
   попытка перенести cookie в отдельно запущенную копию браузера
   зациклила ВК в бесконечных редиректах на проверку входа — ВК считает
   это подозрительным входом с другого устройства, даже если cookie
   настоящая и свежая (Р-013, Р-015).
3. **Токен добыть напрямую нельзя.** Раз браузер получает его неизвестным
   снаружи способом, писать код, который его "вычисляет" из cookie, —
   гадание. Решение прошло два шага (Р-014: слушать сетевые ответы
   headless-браузера; Р-015: подключаться к уже открытому браузеру вместо
   запуска своего) и в итоге пришло к третьему (Р-016): подслушивать
   сетевые ответы изнутри самой вкладки, которую человек и так открыл, —
   расширением браузера, а не отдельной Go-программой. Токеном в этой
   схеме вообще никто не управляет — это забота ВК-фронтенда и настоящей
   сессии человека.
4. **Аудио нам не нужно.** Ссылки на mp3 живут отдельно, они короткоживущие
   и привязаны к сессии. Мы читаем только метаданные — исполнителя, название,
   длительность. Это принципиально другая история и по нагрузке, и по рискам.

## Почему официальный путь не работает

**Метод `audio.get`.** До сих пор есть в документации ВК, и там же указано,
что он требует особых прав доступа. Обычным приложениям эти права не выдают
примерно с 2016–2017 годов.

Обидная деталь: у официального API есть поле `genre` с готовым справочником
из 21 жанра (Rock = 1, Metal = 7, Alternative = 21 и так далее). То есть жанр
там был бы бесплатно. Взять его нельзя, поэтому весь пайплайн обогащения
существует именно из-за этого ограничения.

**Авторизация через VK ID.** Даёт стороннему сайту личность пользователя:
имя, фамилию, аватар, почту, телефон, дату рождения, пол. Аудиозаписей в этом
списке нет. Вход через ВК позволяет узнать, *кто* пришёл, но не даёт доступа
к его музыке.

## Варианты доступа

| Вариант | Как работает | Оценка |
|---|---|---|
| Официальный API `audio.get` | — | Недоступен |
| Токен технического аккаунта | Приложение ходит на внутренние адреса ВК от имени отдельного аккаунта | Отклонён (Р-013) — для закрытых профилей не увидит вообще ничего |
| Cookie личного аккаунта в отдельном браузере | Приложение переносит cookie в свой собственный, отдельно запущенный Chromium | Отклонён (Р-015) — ВК зацикливает вход, считая это подозрительным новым устройством |
| Подключение к уже открытому личному браузеру | Приложение через отладочный порт CDP открывает вкладку в браузере, где человек и так уже залогинен | Отклонён (Р-016) — начиная с Chrome 136 браузер сам отказывается слушать отладочный порт на дефолтном профиле пользователя; способ обхода (отдельный профиль) уже не отличался бы от следующего варианта по сути, только был бы сложнее в реализации |
| Расширение для браузера | Расширение работает прямо внутри вкладки, которую человек и так открыл, слушает её собственные сетевые ответы и отдаёт список треков | Выбрано (Р-016); никакой автоматизации браузера снаружи, ничего не отличимо от обычной вкладки — то же решение, что и было запланировано на v2.0.0, только раньше и с выгрузкой в файл вместо прямой отправки на сервер |
| Официальная выгрузка архива | Пользователь запрашивает архив своих данных в настройках ВК | Полностью официально; готовится часами; только свои данные |
| Импорт из файла | Список подготовлен любым способом и залит файлом | Всегда работает, используется как основной путь при разработке и в тестах |

## Что выбрано и почему

**До релиза:** источник ВК работает от cookie-сессии настоящего личного
аккаунта разработчика — не отдельного технического (Р-013). Причина:
у закрытых профилей (а это основной сценарий проекта) музыка видна только
друзьям; посторонний технический аккаунт не увидел бы её вообще, только
личный аккаунт, уже состоящий в друзьях с владельцем страницы.

**Как именно источник добывает данные (Р-016):** не отдельной Go-программой
и не автоматизацией браузера снаружи (оба пути опробованы в Р-014/Р-015 и
упёрлись в то, что ВК и сам браузер всё лучше отличают "настоящую" вкладку
от управляемой), а расширением, которое человек ставит в свой обычный,
уже залогиненный браузер. Расширение слушает собственные сетевые ответы
открытой вкладки (тот же принцип "не гадать формат, а подслушивать", что
и в Р-014), само докручивает список до конца и собирает из ответов
`artist`/`title`/`duration`/`id` — код разбора почти дословно перенесён
из бывшего `internal/sources/vk/vk.go` на JavaScript. Так не нужно знать,
откуда браузер берёт `access_token`, — это по-прежнему забота самого
ВК-фронтенда, а не нашего кода, и вдобавок не нужно ничего запускать
с параметрами командной строки: расширение работает в самой обычной вкладке.

По кнопке в расширении собранный список скачивается файлом JSON — тем же
самым форматом, что уже понимает `music import file` (v0.4.0). Дальше это
обычный ручной импорт: `music import file tracks.json --library "Имя"`.

Это уже НЕ временное решение для одного человека, как были Р-014/Р-015:
расширение, работающее внутри собственной вкладки пользователя, — это
ровно тот же принцип, что и было запланировано на v2.0.0. Разница
только в передаче результата: сейчас — файл и ручной импорт, в v2.0.0
— прямая отправка на сервер с входом через VK ID (см. ниже). Второе
достраивается поверх первого, а не переписывает его заново.

**Ограничения, встроенные в расширение (а не в Go-код):** пауза между
прокрутками списка и разумный потолок на то, сколько подряд можно
выгрузить, — тот же принцип "не отличаться от человека, листающего
страницу руками", что и был в Р-013, просто перенесённый туда, где он
теперь и выполняется. Аудиофайлы расширение не трогает вообще — читает
только метаданные из уже пришедших ответов.

**После релиза (v2.0.0):** то же самое расширение, но с двумя добавками —
вход через VK ID (чтобы сервер знал, чья это выгрузка) и отправка данных
напрямую на сервер вместо скачивания файла. Для человека выглядит так же —
вставил ссылку, дождался, получил список, — но риск не концентрируется
на одном аккаунте, потому что каждый пользователь ходит своей сессией.

**Всегда:** импорт из файла остаётся как запасной путь. Если источник ВК
однажды перестанет работать, проект продолжит работать — просто список
приедет файлом. Ради этого и придуман интерфейс `TrackSource`.
