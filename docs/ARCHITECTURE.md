## Слои и границы

```
  ИСТОЧНИКИ (сменные)          ЯДРО (не меняется)              ИНТЕРФЕЙС
  ┌─────────────────┐
  │ Файл JSON / CSV │──┐      ┌──────────────────────┐      ┌────────────┐
  │ (в т.ч. выгрузка│  │      │ 1. нормализация      │      │ HTTP API   │
  │ расширения ВК)  │  │  T   │ 2. дедупликация      │      │ веб-стра-  │
  └─────────────────┘  ┼─ r ─▶│ 3. база              │─────▶│ ница       │
  ┌─────────────────┐  │  a   │ 4. обогащение жанрами│      │ CLI        │
  │ Архив выгрузки  │──┘  c   └──────────┬───────────┘      └────────────┘
  └─────────────────┘     k              │
                          S              ▼
                          o    ┌──────────────────────────┐
                          u    │ MusicBrainz · Last.fm ·  │
                          r    │ Deezer                   │
                          c    │ кэш, 1 запрос/сек        │
                          e    └──────────────────────────┘
```

Про ВК в этой схеме больше не написано отдельным источником — начиная
с Р-016 (`docs/DECISIONS.md`) страницу ВК со стороны кода никто не
открывает: этим занимается `extension/`, отдельное браузерное расширение
вне модуля Go, а Go-программа видит только файл JSON, который оно выгружает
(тот же формат, что и у ручного `import file`).

Граница `TrackSource` — главная идея всей конструкции. Это договорённость
вида «источник обязан отдать список треков в одном и том же виде». Всё, что
правее неё, про то, откуда взялся файл, не знает вообще ничего.

Интерфейс в коде выглядит примерно так:

```go
// RawTrack — трек в том виде, в каком его отдал источник.
// Никакой обработки: строки ровно те, что пришли, со всей грязью.
type RawTrack struct {
    Artist      string // "Nirvana", "КиШ", "Король и Шут  "
    Title       string // "Smells Like Teen Spirit (Official Video)"
    DurationSec int    // 301
    SourceID    string // идентификатор внутри источника, если он есть
}

// TrackSource — любой источник треков.
// Файл (в т.ч. выгрузка расширения ВК), архив выгрузки — оба реализуют
// этот интерфейс. Отдельного источника "vk" в Go-коде нет — см. Р-016.
type TrackSource interface {
    // Name возвращает короткое имя источника для журналов: "file".
    Name() string

    // Ref возвращает то, откуда именно брались треки — обычно путь
    // к файлу. Попадает в журнал импортов.
    Ref() string

    // Fetch отдаёт треки. ctx нужен, чтобы операцию можно было прервать —
    // сигнатура одна на все источники, даже если конкретному она не нужна.
    Fetch(ctx context.Context) ([]RawTrack, error)
}
```

«На что смотреть» — путь к файлу или ссылка на страницу — передаётся при
создании источника, а не в каждый вызов. Поэтому у `Fetch` нет лишнего
параметра, а `Ref` может рассказать о себе кому угодно, включая журнал.

Реализация выбирается ровно в одном месте — там, где источник создаётся:

```go
src := file.New(path)     // и для ВК тоже: путь к JSON, который выгрузило extension/
raw, err := src.Fetch(ctx)
```

Всё, что дальше, работает с переменной типа `TrackSource` и про файлы
не знает.

## Схема базы данных

Девять таблиц. Главный принцип: **сырые данные, канонический справочник и
результат сопоставления — три разные вещи, и смешивать их в одной таблице
нельзя.** Благодаря этому обогащение можно перезапускать с нуля, не теряя
ни исходные треки, ни ручные правки.

### Сырое из источника

**`libraries`** — чья коллекция.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | bigserial PK | |
| `title` | text | Название: «Моя музыка», «Рус-Лан» |
| `owner_user_id` | bigint NULL | Владелец. Пока NULL, заполнится с появлением пользователей |
| `source_name` | text | Откуда приехала: `file`, `vk` |
| `source_ref` | text | Что именно: имя файла или ссылка на страницу |
| `visibility` | text | `private` / `link` / `public` |
| `created_at` | timestamptz | |

**`artists`** — исполнители, общие на всё приложение.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | bigserial PK | |
| `name_raw` | text | Первое встреченное написание |
| `name_key` | text UNIQUE | Нормализованный ключ для сравнения |
| `mbid` | uuid NULL | Идентификатор в MusicBrainz, если нашли |
| `created_at` | timestamptz | |

**`artist_aliases`** — разные написания одного исполнителя.

| Колонка | Тип | Смысл |
|---|---|---|
| `alias_key` | text UNIQUE | `киш`, `korol i shut` |
| `artist_id` | bigint → artists | |
| `source` | text | `import` / `manual` / `musicbrainz` |

**`tracks`** — треки, привязаны к библиотеке.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | bigserial PK | |
| `library_id` | bigint → libraries | |
| `artist_id` | bigint → artists | |
| `title_raw` | text | Как пришло |
| `title_key` | text | Нормализованное название |
| `duration_sec` | int NULL | |
| `source_ids` | text[] | Идентификаторы в источнике; массив, потому что дубликаты схлопываются в одну строку |
| `is_present` | boolean | Трек ещё в библиотеке. Позволяет видеть, что удалили |
| `first_seen_at` | timestamptz | |
| `last_seen_at` | timestamptz | |

Уникальный ключ: `(library_id, artist_id, title_key)`.

### Справочник

**`genres`** — канонические жанры с иерархией.

| Колонка | Тип | Смысл |
|---|---|---|
| `id` | serial PK | |
| `code` | text UNIQUE | `rock`, `punk_rock`, `metal` |
| `title_ru` | text | «Рок», «Панк-рок» |
| `parent_id` | int NULL → genres | Родитель. У `punk_rock` это `rock` |

**`genre_aliases`** — соответствие «тег провайдера → наш жанр».

| Колонка | Тип | Смысл |
|---|---|---|
| `alias_key` | text UNIQUE | `hard rock`, `русский рок`, `alt-rock` |
| `genre_id` | int → genres | |
| `source` | text | `seed` (из файла) / `manual` (добавили руками) |

### Результат сопоставления

**`artist_genres`** и **`track_genres`** — одинаковой формы.

| Колонка | Тип | Смысл |
|---|---|---|
| `artist_id` / `track_id` | bigint | |
| `genre_id` | int → genres | |
| `provider` | text | `musicbrainz` / `lastfm` / `deezer` |
| `confidence` | numeric(4,3) | 0.000 … 1.000 |
| `updated_at` | timestamptz | |

Первичный ключ включает `provider`: мнение каждого источника хранится
отдельно, поэтому всегда видно, откуда взялась цифра.

**`overrides`** — ручные правки, применяются последними и всегда побеждают.

| Колонка | Тип | Смысл |
|---|---|---|
| `scope` | text | `artist` или `track` |
| `target_id` | bigint | Идентификатор внутри выбранного scope |
| `genre_id` | int → genres | |
| `action` | text | `add` или `remove` |
| `note` | text | Зачем поправили |

### Журналы

**`provider_cache`** — сырые ответы внешних API.

| Колонка | Тип | Смысл |
|---|---|---|
| `provider` | text | |
| `request_key` | text | `lastfm:artist.getTopTags:nirvana` |
| `response` | jsonb | Ответ целиком, как пришёл |
| `status` | text | `ok` / `not_found` / `error` |
| `fetched_at` | timestamptz | Для проверки срока жизни (30 дней) |

Уникальный ключ: `(provider, request_key)`.

**`import_runs`** и **`enrich_runs`** — история прогонов: когда, сколько
обработано, сколько новых, сколько ошибок. Эти таблицы можно снести целиком
и ничего не сломается — это история, а не данные.

## Пайплайн определения жанра

Схема ниже — исходный план на три провайдера сразу (Р-004). По факту
реализован и используется только Last.fm (v0.7.0); MusicBrainz и Deezer
сознательно отложены — см. Р-018 в `docs/DECISIONS.md`. Схема оставлена как
есть — это готовый план на случай, если к идее вернутся, а не описание
того, что работает прямо сейчас.

```
   исполнитель без жанра
             │
             ▼
   ┌──────────────────┐   есть свежий    ┌──────────────────┐
   │ кэш свежий?      │─────────────────▶│ provider_cache   │
   │ (моложе 30 дней) │       да         │ в сеть не идём   │
   └────────┬─────────┘                  └──────────────────┘
            │ нет
            ▼
   ┌────────────────┬────────────────┬────────────────┐
   │  MusicBrainz   │    Last.fm     │     Deezer     │
   │ 1 запрос/сек   │ теги 0..100    │ жанр альбома   │
   │ нужен UA       │ много шума     │ запасной       │
   └────────┬───────┴────────┬───────┴────────┬───────┘
            └────────────────┼────────────────┘
                             ▼
            сырые теги: rock · хард-рок · seen live · 90s
                             │
                ┌────────────┴────────────┐
                ▼                         ▼
   ┌────────────────────┐    ┌──────────────────────────┐
   │ справочник         │    │ не распознано →          │
   │ тег → жанр         │    │ отчёт /unmapped-tags     │
   └────────┬───────────┘    └──────────────────────────┘
            ▼
   расчёт уверенности → применение ручных правок → artist_genres
```

Кэш стоит **перед** сетью, а не после. Повторный прогон не делает ни одного
запроса наружу. Нераспознанные теги не выбрасываются молча — они копятся
в отчёт, из которого справочник растёт вручную. Это единственный честный
способ довести покрытие до приличного уровня.

### Как считается уверенность

```
сила тега у Last.fm       = count / 100      (Last.fm нормирует топ-тег в 100)
сила тега у MusicBrainz   = 1.0 для genre, 0.6 для обычного тега
сила тега у Deezer        = 1.0 (жанр альбома либо есть, либо нет)

вес провайдера: musicbrainz 0.50 · lastfm 0.35 · deezer 0.15

уверенность(жанр) = min(1.0, Σ вес_провайдера × сила_тега)
```

Формулу можно проверить на калькуляторе за минуту, открыв карточку трека.
Это осознанный отказ от «умного» решения в пользу отлаживаемого.

### Пороги

| Порог | Значение | Что делает |
|---|---|---|
| Совпадение имени | ≥ 88 из 100 | Ниже — считаем, что нашли не того исполнителя. Между 75 и 88 помечаем «нужен глазами». Не реализовано — часть отложенного нечёткого сравнения имён, Р-018 |
| Минимальная уверенность | ≥ 0.50 (план на три провайдера) / **0.15 по факту** | Порог показа в фильтре (`music filter --min`). 0.50 рассчитан на сумму весов всех трёх провайдеров; с одним Last.fm (вес 0.35) он недостижим — фактический порог по умолчанию 0.15, см. Р-019 в `docs/DECISIONS.md` |
| Срок жизни кэша | 30 дней | Через сколько спрашиваем провайдера заново |

## Логика фильтра

Запрос «покажи рок» целиком:

```sql
WITH RECURSIVE genre_tree AS (
    -- шаг 1: берём тот жанр, который попросили
    SELECT id FROM genres WHERE code = 'rock'
    UNION ALL
    -- шаг 2: добираем всех потомков — punk_rock, hard_rock, grunge...
    -- база повторяет этот шаг, пока не перестанет находить новое
    SELECT g.id FROM genres g
    JOIN genre_tree gt ON g.parent_id = gt.id
)
SELECT t.id, a.name_raw AS artist, t.title_raw AS title, ag.confidence
FROM tracks t
JOIN artists a         ON a.id = t.artist_id
JOIN artist_genres ag  ON ag.artist_id = a.id
WHERE t.library_id = $1
  AND ag.genre_id IN (SELECT id FROM genre_tree)
  AND ag.confidence >= $2          -- порог уверенности из запроса
  AND t.is_present                 -- трек ещё в библиотеке
  -- выкидываем то, что помечено вручную как «это не рок»
  AND NOT EXISTS (
      SELECT 1 FROM overrides o
      WHERE o.action = 'remove'
        AND o.genre_id IN (SELECT id FROM genre_tree)
        AND ((o.scope = 'track'  AND o.target_id = t.id)
          OR (o.scope = 'artist' AND o.target_id = a.id))
  )
ORDER BY ag.confidence DESC, a.name_key, t.title_key;
```

`WITH RECURSIVE` — это и есть причина выбора PostgreSQL. Конструкция говорит
базе: «начни с рока, иди по `parent_id` вниз и собирай всё, пока не кончится».
Всё поддерево приходит одним запросом, без перечисления жанров руками и без
цикла в коде приложения.

## Структура репозитория

```
music-genre-filter/
├── .github/workflows/
│   ├── ci.yml               линтер и тесты на каждый push
│   └── release.yml          сборка образа по тегу v*
├── cmd/
│   ├── server/main.go       точка входа HTTP-сервера
│   └── music/main.go        точка входа CLI
├── extension/               ← расширение браузера: выгружает страницу ВК
│                              в JSON того же вида, что понимает file/ (Р-016)
├── internal/
│   ├── config/              чтение настроек из окружения
│   ├── storage/             всё про базу
│   │   ├── db.go            пул соединений и проверка доступности
│   │   ├── migrate.go       накат, откат и статус миграций
│   │   └── genres.go        справочник жанров и обход дерева
│   ├── sources/             ← сменные источники треков
│   │   ├── source.go        интерфейс TrackSource и тип RawTrack
│   │   └── file/            источник из JSON и CSV — им же заводится
│   │                          и выгрузка ВК от extension/
│   ├── normalize/           чистка строк, ключи для сравнения
│   ├── matching/            нечёткое сравнение имён (отложено, Р-018)
│   ├── taxonomy/            тег → канонический жанр
│   ├── enrich/              ← добыча жанра
│   │   ├── provider.go      интерфейс GenreProvider
│   │   ├── lastfm/          единственный провайдер сейчас (v0.7.0)
│   │   ├── musicbrainz/     не реализовано — см. Р-018 в DECISIONS.md
│   │   ├── deezer/          не реализовано — см. Р-018 в DECISIONS.md
│   │   ├── ratelimit/       ограничитель частоты запросов
│   │   └── pipeline.go      кэш → провайдер → теги → уверенность
│   ├── service/             бизнес-логика: импорт, обогащение, фильтр
│   └── web/                 обработчики HTTP и шаблоны
├── migrations/              файлы goose, по одному на изменение схемы
├── scripts/
│   ├── release.ps1          коммит и тег одной командой, текст из CHANGELOG
│   ├── backup_db.sh
│   └── restore_db.sh
├── data/
│   ├── genre_map.json       справочник тег → жанр, растёт руками
│   └── samples/             выдуманный пример для разработки и тестов
├── docs/
├── docker-compose.yml
├── Dockerfile
├── sqlc.yaml
└── go.mod
```

Про ВКонтакте в Go-модуле теперь не знает ни одна папка внутри `internal/` —
это сознательный итог Р-016. Единственное место во всём репозитории, которое
знает про ВК, — `extension/`, и оно нарочно вынесено за пределы Go-модуля:
это отдельная программа на JavaScript, которая живёт в браузере, а не в этом
бинарнике.
