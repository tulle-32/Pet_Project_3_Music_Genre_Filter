# Дорожная карта

Каждый шаг — законченный кусок, который можно запустить и потрогать руками.
Каждый заканчивается коммитом и тегом с одинаковым текстом.

**Статус: проект закрыт на v0.8.0.** Исходная задача («вставил ссылку на
страницу с музыкой → получил список только из рока → выгрузил плейлистом»)
решена целиком — через расширение браузера и командную строку, без веб-сайта
и без Docker-образа. Причина, почему на этом остановились, а не пошли
дальше по изначальному плану (HTTP API, веб-страница, пользователи,
несколько провайдеров жанров) — Р-020 в `docs/DECISIONS.md`: дальнейшее
развитие этого пет-проекта признано менее полезным, чем начать новый,
более амбициозный. Всё, что не сделано, — не забыто, а осознанно
перенесено в раздел «Идеи на будущее» ниже: если когда-нибудь вернёмся
к этому проекту, начинать не с нуля.

## Идеи на будущее (не запланировано)

Здесь не роадмап с версиями, а место для мыслей, которые стоит записать,
чтобы не забыть. Ничего из этого не обязательно когда-либо делать — но
если возвращаться, лучше вернуться сюда, а не изобретать заново.

### Из изначального плана, не реализовано

- **HTTP API и веб-страница.** `/tracks` с фильтром, `/genres`, `/stats`,
  карточка трека с разбором «откуда жанр», а поверх — веб-страница вместо
  терминальной команды. Планировалось как v0.8.0/v1.0.0. Причина не
  делать — Р-020: `music filter` в терминале уже решает задачу, а веб-слой
  добавляет объём работы (роутинг, формы ответов, фронтенд) без новой
  ценности для одного пользователя.
- **Экспорт в `.m3u`, Dockerfile, CI/CD со сборкой образа по тегу.**
  Пока не написан ни один Dockerfile — тег в GitHub сейчас ничего не
  собирает и не публикует, только запускает обычный CI (`gofmt`, `go vet`,
  тесты) на этот коммит. Список треков и так можно перенаправить в файл
  прямо в шелле (`music filter rock --library "..." > список.txt`) —
  отдельная логика экспорта не потребовалась.
- **Ручные правки жанров (`overrides`).** Таблица в схеме базы уже есть и
  учитывается в SQL-запросе `music filter` (строка `NOT EXISTS (... FROM
  overrides ...)`) — но ни одна команда её не заполняет. Если алгоритм
  один раз ошибётся, поправить можно только напрямую в базе SQL-запросом.
- **Второй и третий провайдер жанров (MusicBrainz, Deezer) + сведение
  нескольких мнений в одну уверенность.** В `docs/ARCHITECTURE.md` изначально
  был заложен план на три источника жанров сразу, с формулой сложения их
  уверенности (`Σ вес_провайдера × сила_тега`) и нечётким сравнением имён
  исполнителей между провайдерами. Одного Last.fm хватило, чтобы решить
  исходную задачу — подробности в Р-018 в `docs/DECISIONS.md`.
- **Пользователи, вход через VK ID, права доступа к библиотекам.**
  Таблица `libraries` в схеме с самого начала предусматривает несколько
  владельцев (Р-006), но входа для чужого человека нет — проектом
  пользуется только тот, у кого есть доступ к базе и командной строке.
  Расширение (`extension/`) при этом уже готово к многопользовательскому
  режиму: оно и так работает изнутри чужой залогиненной вкладки, нужно
  только научить его отправлять данные на сервер напрямую вместо
  скачивания файла.
- **Очередь задач и фоновое обогащение.** Сейчас `music enrich run` —
  обычная синхронная команда: пока не закончит (или не прервёшь Ctrl+C),
  терминал занят. Для одного человека и библиотеки в пару тысяч треков
  это не проблема — очередь стала бы решением проблемы, которой не возникло.
- **Метрики Prometheus, дашборд Grafana.** Наблюдаемость имеет смысл для
  сервиса, который работает постоянно и обслуживает больше одного
  человека — сейчас это не тот случай.
- **Перенос CI на self-hosted GitLab.** Отдельное упражнение на сравнение
  двух систем, не связанное с самим проектом.

### Родившиеся по ходу дела

- **Сборка плейлиста обратно в профиль ВК, по жанру.** Сейчас данные текут
  только в одну сторону: из ВК в нашу базу (`extension/`, Р-016 в
  `DECISIONS.md`). Симметричная идея — уметь и обратно: выбрал жанр,
  скажем «рок», нажал кнопку — и в самом ВК на странице пользователя
  появился настоящий плейлист именно из этих треков, без ручного
  перетаскивания. Раз расширение уже умеет работать *изнутри* залогиненной
  вкладки, а не изображать браузер снаружи — оно в теории способно не
  только слушать сетевые ответы, но и самому инициировать запрос на
  создание плейлиста, точно так же, как это делает кнопка «Создать
  плейлист» на самой странице. Это не проработано: неизвестно, какой
  именно запрос ВК отправляет при создании плейлиста и добавлении в него
  треков, стабилен ли этот формат, и не потребует ли он подтверждений,
  которые скриптом не пройти. Если когда-нибудь возвращаемся к этой
  идее — начинать нужно с того же метода разведки, что дал Р-016: открыть
  DevTools, руками создать плейлист и посмотреть, что реально уходит на
  сервер.
- **Команда `library delete` / слияние библиотек.** Всплыло на практике:
  опечатка в названии библиотеки при импорте (`"Рус-лан"` вместо
  `"Рус-Лан"`) создаёт вторую, отдельную библиотеку — `library rename`
  умеет только переименовать, не смержить содержимое двух библиотек
  в одну и не удалить пустышку.

## Правило выпуска версии

Текст тега, сообщения коммита и записи в `CHANGELOG.md` совпадают:

```
v0.4.0 импорт треков из файла: интерфейс источников, нормализация имён, дедупликация
```

Текст набирается один раз — в `CHANGELOG.md`. Дальше выпуск версии это одна
команда, в которой вводится только номер:

```powershell
.\scripts\release.ps1 v0.4.0
```

Скрипт проверяет формат версии, находит в `CHANGELOG.md` заголовок этой
версии, берёт оттуда текст, делает коммит, ставит аннотированный тег с тем же
текстом и отправляет коммиты и тег в GitHub, **проверяя, что тег там
действительно появился**. Ничего, кроме обычного CI (`gofmt`, `go vet`,
сборка, тесты — [.github/workflows/ci.yml](../.github/workflows/ci.yml)),
пуш тега не запускает: Docker-образ и его сборка по тегу были в изначальном
плане (v1.0.0), но проект закрылся раньше — см. «Идеи на будущее» выше.

Посмотреть, что будет сделано, ничего не меняя:

```powershell
.\scripts\release.ps1 v0.4.0 -DryRun
```
