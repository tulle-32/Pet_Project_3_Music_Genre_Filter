Каждое значимое решение записано в одном формате: в каком контексте оно
принималось, что выбрали, и чем за это платим. Записи не редактируются задним

Смысл журнала простой: через три месяца никто, включая автора, не вспомнит,

## Р-001. Источник треков — сменный плагин, а не жёсткая привязка к ВК

**Дата:** 2026-08-23 · **Статус:** принято

**Контекст.** Официальный API ВКонтакте не отдаёт аудиозаписи: метод
`audio.get` требует прав, которые не выдают обычным приложениям. Остаются
обходные пути, и все они хрупкие — они опираются на внутренние адреса ВК,
у которых нет обещаний обратной совместимости. Любой из них может перестать
работать без предупреждения.

**Решение.** Ввести интерфейс `TrackSource`: «источник обязан уметь отдать
список треков в одном и том же виде». Всё, что правее этой границы — база,
нормализация, обогащение, фильтр, API — про ВК не знает ничего. Источник из
файла и источник из ВК становятся двумя равноправными реализациями.

**Последствия.** Плюс: поломка на стороне ВК ломает один файл, а не проект.
Разработку можно вести на файловом источнике, не завися от живого ВК, и тесты
не ходят в сеть. Минус: один лишний уровень косвенности — читая код, надо
понимать, что вызов идёт через интерфейс, а не напрямую.

## Р-002. Язык — Go

**Дата:** 2026-08-23 · **Статус:** принято

**Контекст.** В предыдущем проекте был Python. Правило проекта — брать
технологии, которых ещё не было. Автор переходит в DevOps и хочет понимать
механику кода, а не просто запускать его.

**Решение.** Go.

**Обоснование, помимо очевидного «Go — язык инфраструктурного мира».**
Главный аргумент — отсутствие скрытой магии. В типичном Python-стеке
(FastAPI + SQLAlchemy + Pydantic) значительная часть происходящего невидима:
внедрение зависимостей через `Depends`, декларативные модели, валидация через
метаклассы. Это удобно тому, кто уже знает, как оно работает, и непрозрачно
тому, кто учится. В Go путь запроса читается сверху вниз, каждая ошибка
обрабатывается явной строкой, SQL пишется руками. Дополнительно: компилятор
ловит опечатки до запуска, а итоговый образ весит порядка 20 МБ вместо 150.

**Последствия.** Плюс: код прозрачнее, ошибок времени выполнения меньше,
Docker-образ маленький, зависимостей меньше — HTTP-сервер, шаблоны, JSON и
тесты есть в стандартной библиотеке. Минус: строк кода больше из-за явной
обработки ошибок; библиотек для нечёткого сравнения строк меньше, чем в
Python, поэтому алгоритм сравнения будем писать сами.

## Р-003. База — PostgreSQL, доступ через sqlc, без ORM

**Дата:** 2026-08-23 · **Статус:** принято

**Контекст.** В предыдущем проекте был SQLite с ручной миграцией схемы через
`ALTER TABLE`. Здесь нужны дерево жанров с произвольной глубиной, массивы
идентификаторов и хранение сырых ответов внешних API.

**Решение.** PostgreSQL. Миграции — через `goose`, файлы миграций встроены
в бинарник. Запросы пишутся обычным SQL; начиная с v0.4.0 из `.sql`-файлов
будет генерироваться типизированный Go-код через `sqlc`. В v0.3.0 запросов
ещё мало, поэтому генератор пока не подключали — это была бы церемония
без содержания.

**Обоснование.** Дерево жанров разворачивается рекурсивным запросом
(`WITH RECURSIVE`) — «покажи рок» одним запросом захватывает панк-рок,
хард-рок и гранж. В SQLite это возможно, но неудобно. JSONB нужен для сырых
ответов провайдеров, массивы — для идентификаторов треков в источнике.
Отказ от ORM осознанный: видно ровно те запросы, что уходят в базу, и попутно
подтягивается настоящий SQL — навык, который в DevOps нужен и сам по себе.

**Последствия.** Плюс: миграции версионируются, откат предусмотрен, магии нет.
Минус: перед каждой сборкой нужен шаг генерации кода из SQL; в CI это ещё
один шаг.

## Р-004. Жанр берётся из внешних справочников и снабжается уверенностью

**Дата:** 2026-08-23 · **Статус:** принято

**Контекст.** В данных, которые отдаёт ВК, поля жанра нет: только исполнитель,
название и длительность. Поле `genre` существует в официальном API, но он нам
недоступен.

**Решение.** Опрашивать MusicBrainz, Last.fm и Deezer, сводить их ответы к
собственному справочнику жанров и хранить для каждой пары «исполнитель — жанр»
число уверенности от 0 до 1. Формула — взвешенная сумма мнений провайдеров.

**Обоснование.** Уверенность нужна, чтобы результат можно было проверить
руками: открыв карточку трека, видно, какой провайдер что предложил и с каким
весом. Альтернатива — отдавать жанр без объяснений — превращает ядро проекта
в чёрный ящик, который невозможно отладить.

**Последствия.** Плюс: результат объясним и проверяем. Минус: появляются
пороги, которые придётся подбирать опытным путём, и справочник соответствий
«тег → жанр», который растёт вручную.

## Р-005. Кэш на уровне исполнителя, а не трека

**Дата:** 2026-08-23 · **Статус:** принято

**Контекст.** MusicBrainz разрешает один запрос в секунду с адреса. В
библиотеке около 1900 треков, но уникальных исполнителей среди них 500–700.

**Решение.** Спрашивать жанр про исполнителя, а не про каждый трек. Все ответы
складывать в таблицу `provider_cache` со временем жизни 30 дней.

**Последствия.** Плюс: первое обогащение занимает минуты вместо получаса,
повторный прогон не делает ни одного запроса наружу, а справочник исполнителей
общий на всё приложение — вторая залитая библиотека обогащается почти мгновенно.
Минус: жанр по исполнителю — упрощение. У группы бывает акустический альбом,
у рэпера — фит с металлистами. Компенсируется уровнем трека и ручными правками.

## Р-006. Таблица библиотек закладывается сразу, пользователи — позже

**Дата:** 2026-08-23 · **Статус:** принято

**Контекст.** В перспективе приложением пользуется не один человек: каждый
приносит свою коллекцию и может показать её другим. Но полноценный
многопользовательский режим с авторизацией — это отдельный объём работы,
который отодвинет первый полезный результат.

**Решение.** Таблицу `libraries` (чья коллекция, кто владелец, кому видна)
добавить в схему сразу, с первой версии, даже пока библиотека одна. Таблицу
`users` и вход через VK ID — отдельной версией после релиза.

**Обоснование, и это общее правило.** Дёшево откладывать то, что добавляется
новой таблицей. Дорого — то, что меняет ключи и связи в уже заполненных
таблицах. Добавить `library_id` в `tracks` потом означает миграцию с переносом
данных и сменой уникального ключа с `(artist_id, title_key)` на
`(library_id, artist_id, title_key)`. Сейчас это ноль работы.

**Последствия.** Плюс: переход к многопользовательскому режиму не потребует
переделки данных. Минус: в первых версиях в коде будет колонка, которая
всегда содержит одно и то же значение, и это выглядит избыточно.

## Р-007. Очередь задач откладывается

**Дата:** 2026-08-23 · **Статус:** принято

**Контекст.** Обогащение жанрами — долгая операция с обращениями к внешним
API. Классическое решение — вынести её в фоновую очередь.

**Решение.** В первых версиях обогащение работает синхронно и честно ждёт.
Очередь появится отдельной версией после релиза, если понадобится.

**Обоснование.** Очередь, добавленная до того, как проблема проявилась, —
это сложность без причины. Сначала нужно увидеть своими глазами, как прогон
на 600 исполнителей занимает двенадцать минут, и только тогда очередь станет
решением конкретной боли, а не украшением архитектуры.

**Последствия.** Плюс: на две движущиеся части меньше в первых версиях.
Минус: до появления очереди HTTP-запрос на обогащение будет долго висеть, и
на это придётся выставлять большие таймауты.

## Р-008. CI/CD — GitHub Actions, GitLab CI позже

**Дата:** 2026-08-23 · **Статус:** принято

**Контекст.** Репозиторий на GitHub. Автор не работал с CI/CD ни в теории,
ни на практике, и хочет разобраться. GitLab CI был обозначен как интересное
направление.

**Решение.** Начинаем с GitHub Actions. Перенос пайплайна на self-hosted
GitLab CI — возможная отдельная версия после релиза.

**Обоснование.** Свой GitLab означает сначала администрировать GitLab, а
потом уже изучать CI. Это два незнакомых дела одновременно. На Actions
пайплайн заводится одним YAML-файлом, а когда механика станет понятной,
перенос в GitLab будет осознанным сравнением двух систем.

**Последствия.** Плюс: первый работающий пайплайн получается на несколько
недель раньше. Минус: привязка к конкретной платформе, но она снимается
переносом.

## Р-009. Тексты тега, коммита и журнала изменений совпадают

**Дата:** 2026-08-23 · **Статус:** принято

**Контекст.** Одна и та же формулировка нужна в трёх местах: сообщение
коммита, аннотация git-тега, строка в `CHANGELOG.md`. Руками они рано или
поздно разъедутся.

**Решение.** Формат: `vX.Y.Z короткое описание с маленькой буквы`.
Единственный источник правды — `CHANGELOG.md`: заголовок версии пишется там
один раз. Скрипт `scripts/release.ps1` читает этот заголовок и подставляет
его и в сообщение коммита, и в аннотацию тега. Вводить текст руками вообще
не приходится — только номер версии.

**Последствия.** Плюс: разъехаться нечему, потому что текст ровно один.
Забыть описать версию в журнале изменений тоже не выйдет — скрипт откажется
работать, пока записи нет. Минус: скрипт написан под PowerShell и потому
привязан к Windows. Когда релизы начнут выпускаться из Linux или из
пайплайна, понадобится второй вариант на bash.

## Р-010. Генератор sqlc не берём, запросы пишем руками

**Дата:** 2026-08-23 · **Статус:** принято, отменяет часть Р-003

**Контекст.** В Р-003 планировалось писать SQL в отдельных файлах и
генерировать из них типизированный Go-код через `sqlc`. К v0.4.0 запросов
набралось около десятка, и стало видно, какие они: рекурсивный обход дерева,
вставка с разрешением конфликта, объединение массивов, приём с системной
колонкой `xmax`. То есть немного, но каждый нетривиальный.

**Решение.** `sqlc` не подключаем. Запросы остаются обычным SQL внутри
Go-файлов, рядом с кодом, который их вызывает и комментирует.

**Обоснование.** `sqlc` силён там, где запросов много и они однотипные:
он экономит написание сотен структур руками. У нас обратная картина —
запросов мало, и каждый требует комментария на пять строк. Выигрыш
получился бы копеечный, а цена вполне ощутимая: ещё один обязательный
исполняемый файл на каждой машине разработчика и ещё один шаг генерации
в сборке и в пайплайне.

**Последствия.** Плюс: чтобы собрать проект, достаточно Go и Docker.
Минус: соответствие между колонками запроса и аргументами `Scan`
компилятор не проверяет — ошибка вылезет в момент выполнения. Лечится
тестами на слой хранения. Решение пересмотрим, если однотипных запросов
станет много.

## Р-011. Как нормализуются имена: три спорных решения

**Дата:** 2026-08-23 · **Статус:** принято

**Контекст.** Строки из ВКонтакте набивали люди пятнадцать лет. Чтобы
понять, что `NIRVANA` и `  nirvana  ` — один исполнитель, строки надо
приводить к общему виду. Каждое правило приведения — это выбор между
«схлопнуть лишнее» и «не схлопнуть нужное».

**Решение первое: `&` не считается разделителем участников.** `Simon &
Garfunkel`, `Mott & Bailey` — цельные названия коллективов. Разделителями
считаются только явные `feat.`, `ft.`, `при участии` и им подобные.

**Решение второе: берётся основной исполнитель.** `Miyagi feat. Andy Panda`
превращается в `Miyagi`, потому что внешние справочники знают именно
`Miyagi`, а строку целиком не найдут — и трек останется без жанра.

**Решение третье: скобки удаляются выборочно.** Не подряд, а только те,
внутри которых есть слово из списка мусора: `official`, `video`, `hd`,
`ремастеринг` и ещё три десятка. Иначе `(I Can't Get No) Satisfaction`
лишилось бы половины названия.

**Последствия.** Первое решение имеет видимую цену: `Miyagi` и
`Miyagi & Andy Panda` остаются разными исполнителями, и совместный трек
попадает в базу дважды. Это осознанный размен: ложное разделение чинится
записью в `artist_aliases`, а ложное склеивание двух разных групп —
ничем. Нечёткое сравнение имён в v0.8.0 такие случаи будет находить
и предлагать к объединению.

## Р-012. В CI пока только gofmt и go vet, без golangci-lint

**Дата:** 2026-08-24 · **Статус:** принято

**Контекст.** golangci-lint — стандартный в индустрии инструмент: он
запускает разом несколько десятков отдельных линтеров и настраивается
одним файлом `.golangci.yml`. Это и есть основная сложность для первого
пайплайна: он либо ругается почти ни на что (конфиг по умолчанию скромный),
либо требует сразу разбираться, какие из полусотни проверок включить,
а какие выключить и почему — а цель v0.5.0 в том, чтобы понять механику
CI как таковую, а не механику одного конкретного линтера.

**Решение.** Первый пайплайн проверяет форматирование через `gofmt -l`
и очевидные ошибки через `go vet` — оба инструмента идут в поставке
Go, ничего дополнительно устанавливать и настраивать не нужно.
golangci-lint остаётся кандидатом на подключение позже, когда в проекте
наберётся достаточно кода, чтобы почувствовать разницу между "линтер
для вида" и "линтер, который реально что-то ловит".

**Обоснование.** У пайплайна из четырёх понятных шагов (формат, vet,
сборка, тесты) видно ровно то, что он делает — можно прочитать
`ci.yml` целиком за минуту и понять весь путь `git push` → результат.
Пайплайн с golangci-lint потребовал бы ещё и вчитываться в чужой
конфиг с полусотней флагов, прежде чем стало бы понятно, что вообще
проверяется.

**Последствия.** Плюс: первый пайплайн получился маленьким и полностью
прозрачным — то, что нужно для темы "разобраться в CI с нуля". Минус:
`go vet` ловит существенно меньше, чем полноценный линтер (например,
не проверяет неиспользуемые переменные во всех случаях, не ищет
типичные ошибки вроде игнорирования возврата ошибки). Отслеживается —
решение пересмотрим, когда объём кода сделает это ощутимым.

## Р-013. Источник ВК — сессия личного аккаунта, а не технического

**Дата:** 2026-08-24 · **Статус:** принято, отменяет описание в docs/VK_ACCESS.md

**Контекст.** Изначальный план (см. `docs/VK_ACCESS.md`, раздел «Что
выбрано») предполагал завести отдельный технический аккаунт специально
под скрейпинг. Проверка руками (открыли страницы Рус-Лана, папы и жены
в режиме инкогнито) показала: у большинства реальных профилей музыка
или вся страница видна только друзьям. Аккаунт, ни с кем не в друзьях,
— для ВК посторонний человек с улицы; он увидит ровно то же самое, что
видно в инкогнито: ничего. То есть технический аккаунт не просто более
рискованный вариант — он **не решает исходную задачу** для закрытых
профилей, а закрытые профили и есть основной сценарий проекта. Заодно
выяснилось, что регистрация нового аккаунта в ВК требует номер телефона
(похоже, преимущественно российский) — ещё один аргумент не плодить
технические аккаунты без необходимости.

**Решение.** Источник ВК работает от cookie сессии **настоящего личного
аккаунта** — того, кто уже состоит в друзьях с людьми, чью музыку хочет
получить. Пока приложением пользуется один человек — это его основной
аккаунт, риск принят осознанно. Переменная в `.env` переименована из
`VK_TOKEN` в `VK_SESSION_COOKIE`, потому что это не токен API, а
буквально содержимое заголовка `Cookie` из залогиненного браузера.

**Обоснование.** Приложение должно видеть ВК ровно так же, как видит его
человек, от чьей сессии оно работает. Раз человек — настоящий друг
владельца страницы, приватность «только друзьям» открывается сама, без
обхода. Альтернатива (расширение для браузера, где каждый пользователь
ходит своей сессией) остаётся верным решением на будущее и уже
запланирована на v2.0.0 — это тот же принцип «сессия того, кто реально
видит контент», просто в многопользовательском виде.

**Последствия.** Плюс: источник ВК реально работает на закрытых профилях
друзей, а не только на полностью публичных страницах. Минус, принят
осознанно: автоматические запросы идут от настоящего личного аккаунта, и
теоретически могут выглядеть для ВК подозрительно — крайний случай
здесь не потеря аккаунта, а требование повторно подтвердить, что это
владелец (капча, проверка входа). Отсюда встроенные ограничители остаются
обязательными и не смягчаются: пауза не меньше 2 секунд между запросами,
суточный потолок на количество выгрузок, кэширование, только метаданные —
поведение должно быть неотличимо от человека, листающего страницу руками.

## Р-014. Источник ВК ходит через headless-браузер, а не собирает запросы вручную

**Дата:** 2026-08-24 · **Статус:** принято, отменяет описание запроса ② в docs/VK_ACCESS.md

**Контекст.** Разведка (`music vk probe`, v0.5.1) и разбор полного HAR-снимка
настоящей сессии показали: список из `docs/VK_ACCESS.md` (`POST m.vk.ru/audio
act=load_section`) устарел. Реальный современный путь — `POST
web.api.vk.ru/method/catalog.getAudio` (первая страница) и `.../catalog.getSection`
(пагинация опорным курсором), и оба требуют не только cookie, а ещё
отдельный `access_token` вида `vk1.a....`. Попытка найти, откуда браузер
берёт этот токен, чтобы получить его так же в Go, зашла в тупик:

- в HTML самой страницы токена нет (проверено регуляркой по сырой странице);
- вызов, который выглядел как выдача токена (`eventHub.getToken`), на самом
  деле принимает токен на вход, а не выдаёт его;
- единственный найденный вызов, где токен вообще фигурирует до его
  использования (`POST login.vk.ru/?act=web_token`), **подтверждает** уже
  готовый токен, а не создаёт новый — на входе и на выходе буквально одна
  и та же строка;
- дальше искать некуда: HAR по устройству не показывает cookie-заголовки
  (DevTools вырезает их из экспорта) и тем более не показывает localStorage
  или IndexedDB браузера — а токен почти наверняка живёт именно там,
  оставшись с более раннего входа в аккаунт, которого не было в записи.

Иными словами: этот токен — не что-то, что можно вывести из cookie одной
формулой. Он либо рождается в момент, которого нет в нашей записи трафика,
либо хранится в браузере способом, который в принципе не виден снаружи.
Написать код, который его добывает без браузера, означало бы гадать
в третий раз подряд после уже двух не подтвердившихся догадок
(`act=load_section`, затем гипотеза про `eventHub.getToken`) — а именно
от такого гадания мы осознанно отказались, когда решили сначала делать
разведку (v0.5.1), а потом код.

**Решение.** `internal/sources/vk` не собирает HTTP-запросы к
`web.api.vk.ru` вручную. Вместо этого он открывает страницу
`vk.ru/audios<owner_id>` в headless-браузере (Chromium через `chromedp`),
подставляет туда `VK_SESSION_COOKIE`, даёт странице выполнить свой
собственный JavaScript как обычно — включая то, что бы он ни делал для
получения `access_token`, — и слушает через протокол DevTools (CDP)
сетевые ответы, которые сам браузер получает от `catalog.getAudio` и
`catalog.getSection`. Прокрутка страницы (или эквивалентное действие)
запускает у браузера пагинацию так же, как у живого человека.

**Обоснование.** Токен добывает тот, кто и должен его добывать, — настоящий
браузер с настоящим JS-кодом ВК, которому ВК сам его выдаёт. Мы не
разбираемся, как именно рождается `access_token`, и не обязаны это знать:
любой внутренний контракт (название параметра, алгоритм, куда токен
прячется) может измениться у ВК в любой момент, а подписка на сетевые
ответы браузера этого не заметит — сломается только если ВК полностью
поменяет форму HTML-страницы или разлогинит нашу cookie-сессию, что
и так было бы концом работы для любого варианта.

**Последствия.** Плюс: устойчивость к точной внутренней механике ВК —
источник не привязан к конкретному эндпоинту, параметру или способу
получения токена, только к тому, что "открытие страницы с музыкой в
браузере в итоге показывает треки". Минус: тяжёлая зависимость
(headless Chromium) и заметно более медленный и более ресурсоёмкий
запрос, чем прямой HTTP POST, — счётчики `VK_REQUEST_DELAY_SECONDS` и
`VK_DAILY_FETCH_LIMIT` из Р-013 не смягчаются, они как раз и рассчитаны
на то, что каждый заход — это действие, похожее на человека, а не серия
дешёвых запросов. `docs/VK_ACCESS.md` требует правки — описание запроса
② там ещё старое.

## Р-015. Headless-браузер подключается к уже открытому браузеру, а не запускает свою копию

**Дата:** 2026-08-24 · **Статус:** принято, уточняет реализацию Р-014

**Контекст.** Первая версия Р-014 запускала отдельный, новый процесс
Chromium и переносила в него `VK_SESSION_COOKIE` вручную. На первом же
живом запуске против настоящего профиля это привело к зацикленным
редиректам на `login.php?act=slogin&role=fast` — ВК не пускал дальше,
хотя cookie была настоящей и свежей. Диагностика по шагам:

- в самом Яндекс.Браузере (откуда и была скопирована cookie) вход
  проходит без единого вопроса — значит, аккаунт не заблокирован и
  повторного подтверждения в принципе не требует;
- то же самое, но в новом, отдельно запущенном Chromium с той же самой
  cookie — зацикленный редирект, и маскировка типичных признаков
  автоматизации (User-Agent, флаг `enable-automation`, подмена
  `navigator.webdriver`) картину не поменяла.

Вывод: дело не в cookie и не в очевидных флагах автоматизации, а в том,
что ВК связывает сессию не только с cookie, а ещё с чем-то, что
принадлежит конкретному браузерному процессу целиком — набором шрифтов,
расширениями, TLS-стеком и так далее. Копия cookie в другом процессе —
это, с точки зрения ВК, тот же человек внезапно зашёл с другого
устройства, и это ровно тот случай, о котором честно предупреждала
Р-013 ("Последствия"): требование повторно подтвердить, что это
владелец.

**Решение.** `internal/sources/vk` больше не запускает свой собственный
процесс браузера и не переносит в него cookie. Вместо этого он
подключается по протоколу DevTools (CDP) к **уже открытому** браузеру
пользователя (Яндекс.Браузер, запущенный с параметром
`--remote-debugging-port`), в котором человек и так залогинен в ВК как
обычно, и открывает страницу с музыкой новой вкладкой в этом же самом
браузере. `VK_SESSION_COOKIE` источнику `import vk` больше не нужна
(команда `music vk probe` — отдельный инструмент, ей всё ещё пользуется).
Новая настройка — `VK_DEBUG_PORT` (порт, на котором браузер слушает CDP).

**Обоснование.** Это не отказ от идеи Р-014, а её доведение до рабочего
состояния: суть Р-014 была в том, чтобы не изображать браузер, а
пользоваться настоящим и слушать его настоящие ответы. Здесь тот же
принцип доведён на шаг дальше — не изображать даже сам браузерный
процесс: используется тот, которому ВК и так уже доверяет, потому что
это буквально он и есть, без единой скопированной cookie.

Важная оговорка на будущее — это решение для v1, где приложением
пользуется один человек (сам разработчик), который может открыть свой
браузер с нужным параметром вручную. Это НЕ образец того, как источник
ВК будет работать для чужих пользователей после релиза: план v2.0.0
(расширение для браузера, см. `docs/VK_ACCESS.md`) устроен принципиально
иначе — оно выполняется внутри вкладки, которую человек и так уже открыл
в своём обычном браузере, и ему не нужно ничего запускать с параметрами
командной строки. Подключение по отладочному порту — временная техника
ровно на то время, пока проект личный.

**Последствия.** Плюс: реальный запуск на закрытом профиле Рус-Лана либо
работает, либо нет по причине, которая видна и понятна (браузер не
запущен с нужным портом, вкладка закрыта и так далее) — а не тонет в
догадках про cookie и антибот-флаги. Минус: работать может, только пока
у пользователя открыт браузер с этим параметром, — на автоматический
ночной запуск без присмотра это не рассчитано (что для v1 и не нужно).
`VK_CHROME_PATH` и `VK_HEADLESS`, добавленные вместе с первой версией
Р-014, для `import vk` больше не используются.

## Р-016. Источник ВК — расширение браузера, а не автоматизация снаружи

**Дата:** 2026-08-24 · **Статус:** принято, отменяет Р-015 (Р-013 и Р-014
остаются в силе как часть общей картины — см. «Обоснование»)

**Контекст.** Р-015 требовал заранее запустить браузер с параметром
`--remote-debugging-port` на дефолтном, уже залогиненном профиле. На
практике это не заработало: браузер открывался нормально, но порт не
начинал слушать вообще ни при каких условиях — ни после полного завершения
всех процессов браузера, ни при точном соответствии команды запуска
документации. Проверка показала причину: начиная с Chrome 136 (апрель
2025), Google сознательно отключили `--remote-debugging-port` и
`--remote-debugging-pipe` для дефолтного каталога данных браузера —
именно потому, что через отладочный порт вредоносные программы воровали
куки из настоящего, уже залогиненного профиля. Яндекс.Браузер собран на
свежем Chromium (Chrome/150 в User-Agent) и унаследовал это ограничение.
Формально это не баг и не ошибка конфигурации — это осознанное решение
самого Chrome закрыть ровно ту дверь, через которую заходила Р-015.

Обходной путь существовал (запускать браузер с отдельным, не дефолтным
`--user-data-dir`, куда предварительно скопирована или заведена вручную
копия профиля) — но, начав его разбирать, стало видно, что решение
получается сложнее самого следующего варианта и по сути превращается
в него же: и то и другое требует человеку заранее что-то готовить
(отдельный профиль, флаги командной строки), и то и другое хрупкое
к очередному ужесточению со стороны Chrome или ВК. Разговор с автором
проекта в этот момент явно поставил вопрос: мы третий раз подряд чиним
симптом одной и той же болезни (программа снаружи пытается притвориться
человеком в браузере), а не убираем причину.

**Решение.** Источник ВК — это больше не Go-код и не автоматизация браузера
снаружи. Это расширение браузера (`extension/`, отдельная программа на
JavaScript вне модуля Go), которое устанавливается в обычный, уже
залогиненный браузер человека и работает изнутри той вкладки, которую он
и так открыл сам. Расширение слушает собственные сетевые ответы страницы
(тот же способ разбора, что был в `internal/sources/vk/vk.go`: рекурсивный
поиск массива `audios` в ответах `web.api.vk.ru/method/`, теперь
переписанный на JavaScript), само докручивает список до конца и по кнопке
отдаёт собранные треки файлом JSON — в точности том формате, который уже
понимает `music import file` (v0.4.0). `internal/sources/vk` (и `vk.go`,
и разведочный `probe.go` из v0.5.1) удалены из репозитория целиком, вместе
с командами `import vk` и `vk probe` в `cmd/music` и настройками
`VK_DEBUG_PORT`/`VK_SESSION_COOKIE` в конфиге — они предназначались ровно
для той механики, которой больше нет.

**Обоснование.** Р-013 и Р-014 не были потрачены впустую — они остаются
верными в своей сути и просто переезжают в новый исполнитель:

- Р-013 (сессия настоящего личного аккаунта, а не технического) — всё ещё
  верно, просто теперь это не cookie в `.env`, а обычный вход человека
  в свой браузер, каким он и так пользуется;
- Р-014 (не собирать запросы к `web.api.vk.ru` руками, а слушать настоящие
  ответы браузера) — всё ещё верно, просто "слушателем" теперь выступает
  расширение внутри вкладки, а не CDP снаружи неё.

Ключевая разница с Р-014/Р-015 в том, ГДЕ выполняется слушающий код.
Р-014 и Р-015 пытались быть достаточно похожими на настоящий браузер
(сначала — скопировать cookie в новый процесс, потом — подключиться к
чужому процессу по отладочному протоколу). Оба раза выяснялось, что
"похоже на настоящее" — это движущаяся цель: то ВК отличает браузерный
процесс по отпечатку, то сам браузер закрывает дверь, через которую
подключались. Расширение эту гонку прекращает не потому, что маскируется
лучше, а потому, что ему не нужно ничего изображать — оно физически и
есть часть той самой вкладки, к которой ни у ВК, ни у Chrome нет и не
может быть претензий.

Дополнительный, отдельно важный эффект: то, что раньше было честной
оговоркой "решение только для v1, не так будут пользоваться реальные
люди" (см. Р-015), теперь этой оговорки не требует. Расширение,
работающее в собственной вкладке пользователя, — это ровно тот же
принцип, что уже был запланирован на v2.0.0. Автор проекта прямо
поднял этот вопрос при обсуждении, и ответ на него встроен в само
решение, а не просто записан отдельно: v0.6.0 и v2.0.0 теперь — это
один и тот же механизм, различающийся только тем, куда уходит
собранный список (файл на диск против сервера с входом через VK ID).

**Последствия.** Плюс: вся гонка с ВК и Chrome за версии Р-013–Р-015
прекращается — расширению нечего прятать и не от чего защищаться. Плюс:
`internal/sources/vk` больше нет — из Go-модуля ушёл единственный кусок
кода, требовавший тяжёлую зависимость (`chromedp`, headless Chromium) и
не поддающийся автоматическим тестам без живого браузера. Минус: у
проекта появляется вторая программа на другом языке (`extension/`, JS) —
это осознанная плата, а не случайное усложнение: расширение обязано жить
внутри браузера, Go туда добраться не может в принципе. Минус: ручной шаг
никуда не делся — человеку по-прежнему нужно поставить расширение (один
раз) и запустить `music import file` после каждой выгрузки, пока не
сделан v2.0.0 с прямой отправкой на сервер. `docs/VK_ACCESS.md` и
`docs/ARCHITECTURE.md` обновлены под эту картину.

**Проверено** (запись по факту первого живого использования, подробности
и цифры — в `CHANGELOG.md`, v0.6.0): страница Рус-Лана, 1918 треков,
итоговый прогон нашёл все 1918 без дублей. Первый прогон нашёл 1898 —
не архитектурная проблема Р-016, а слишком нетерпеливый порог остановки
прокрутки, унаследованный из старого vk.go без переосмысления под новые
условия; исправлено в самом расширении, решение не поменялось.
